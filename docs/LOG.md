# Журнал эксперимента

## 2026-11-21 — Подготовка окружения и тулинга

**Цель сессии:** понять порядок работы и настроить инструменты, чтобы агент мог работать с GitHub.

**Решения:**
- Задачи и баги ведём в GitHub Issues, агент читает их через `gh`.
- Пользовательские истории храним в репозитории (`docs/SPEC.md`, `docs/stories/*.md`), а не в issues: они версионируются вместе с кодом и не «закрываются».
- Ревью PR — Bugbot (локально через `/review-bugbot` или облачный через GitHub-интеграцию).
- Порядок работы: спецификация → выбор стека → `AGENTS.md` → скелет + CI → нарезка задач → цикл «issue → PR → ревью → merge».

**Сделано:**
- Добавлен `shell.nix` (rustup, wasm-pack, sfz, gh), запушен в `main`.
- `gh` залогинен, протокол SSH, права `repo`, `workflow`.
- `git` и `gh` добавлены в allowlist команд Cursor.
- Проверено: агент видит `git`, `gh`, `cargo 1.99.1`, цель `wasm32-unknown-unknown`; доступ к `origin` по SSH работает.

**Что не получилось с первого раза:**
1. Агент не смог запустить shell (`Failed to exec /run/current-system/sw/bin/bash`), а потом не нашёл `git`. Причина: команды агента идут в песочнице, где не виден `/run/current-system` (системные пакеты NixOS). У пользователя в терминале всё работало.
2. `gh auth status` у агента показывал «token invalid», хотя пользователь был залогинен. Причина: токен в keyring, доступ к нему идёт через D-Bus, а сокет D-Bus в песочнице недоступен.
   - Решение для обоих пунктов: добавить `git` и `gh` в allowlist (Cursor Settings → Agents → Approvals & Execution). Такие команды выполняются вне песочницы.
3. Если агент сам запрашивает для команды сетевое разрешение, она уходит в песочницу даже при наличии в allowlist и падает без `git`.
4. Перелогин `gh` на SSH оказался не обязателен (`origin` и так был по SSH), но при этом пропало право `workflow`. Вернули через `gh auth refresh -s workflow`.
5. Агент в режиме Ask не может создавать файлы — этот журнал пришлось записывать отдельно.

**Ручное вмешательство:** вся настройка окружения (`shell.nix`, логин `gh`, allowlist, коммит) — руками; агент диагностировал и советовал.

**Следующий шаг:** спецификация в новом чате в режиме Agent.

## 2026-11-21 — Спецификация продукта

**Цель сессии:** сформулировать продуктовую спецификацию и пользовательские истории первой версии. Стек не выбираем, код не пишем.

**Формат работы:** агент задавал по одному-два вопроса за раз, ничего не придумывая за пользователя (22 вопроса), затем предложил план документов и после согласия с поправками записал файлы.

**Решения:**
- Покупкомер — веб-приложение для учёта личных финансов, для одного человека; сначала для автора, но сразу пригодное для других. Общего доступа нет.
- Мотивация: в EasyFinance и ZenMoney непонятно планирование и нельзя смотреть траты по подкатегориям. Долгосрочная цель — план из истории (среднее за 3 полных прошлых месяца по категории) и сравнение с ним текущего месяца.
- Первая версия — фундамент для данных: вход, настройка категорий, счета, ввод операций, быстрый доступ к остаткам и долгам, отчёт по категориям. Планирование — через несколько месяцев, когда будут данные.
- Вход через Google-аккаунт, данные в Google Drive (Application Data folder). Собственного сервера нет — жёсткое требование, в том числе для авторизации.
- Счета с валютой и начальным остатком; несколько валют без базовой валюты и пересчёта.
- Одно дерево категорий из двух уровней; у категории признак «для расходов / доходов / обоих»; подкатегория наследует настройки родителя. Удаление категории — с переносом операций в выбранную категорию.
- Операции: расход, доход, перевод (две суммы при разных валютах), дать в долг, взять в долг, частичный возврат долга. Автоматический порядковый номер внутри дня.
- Главный экран — лента последних операций и быстрое добавление.
- Не в первой версии: планирование, импорт, базовая валюта и курсы, офлайн/PWA, закрытие счетов, фильтры, метки/магазины/разбивка чека.

**Сделано:**
- `docs/SPEC.md` — что это, для кого, понятия, сценарии, что не входит, открытые вопросы.
- `docs/stories/001…014` — по файлу на историю, критерии приёмки в формате Дано/Когда/Тогда.

**Что не получилось с первого раза:**
1. Агент сразу ушёл в планирование (как считать среднее, как сравнивать середину месяца), хотя это задача второй-третьей очереди. Пользователь вернул к основе: сначала ввод операций, категории и счета.
2. В плане документов агент назвал «список операций», не пояснив, что имеет в виду; пришлось уточнять. Выяснилось, что это главный экран приложения.
3. Агент неверно предположил отдельные деревья категорий для расходов и доходов.
4. В историю входа агент сначала заложил вариант с минимальным сервером для refresh token; после решения «без сервера» критерии ослаблены: пароль не вводится, но допускается одно нажатие для подтверждения через Google.
5. Агент дописал в истории очевидные, на его взгляд, правила, о которых не спрашивал (выход, запрет перевода на тот же счёт и т. п.), и перечислил их отдельно для проверки.

**Ручное вмешательство:** только ответы на вопросы и поправки; документы целиком написал агент.

**Открытые вопросы** (отложены, список в `docs/SPEC.md`): стартовый набор категорий, операции в категории верхнего уровня, выбор контрагента, модель возврата долга, период отчётов и др.

**Следующий шаг:** организация процесса — выбор стека, `AGENTS.md`, скелет + CI, нарезка задач.
