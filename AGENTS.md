# Правила работы агентов

Покупкомер — веб-приложение на Rust + WASM. Что делаем: `docs/SPEC.md`, истории с критериями приёмки: `docs/stories/*.md`. Порядок реализации: `docs/ROADMAP.md`. Задачи — GitHub Issues (`gh issue view N`).

## Старт сессии

Пользователь не обязан напоминать процесс. В начале работы над разработкой:

1. Открыть `docs/ROADMAP.md` и взять **первую** историю, для которой ещё нет закрытого Issue (или Issue ещё не создан).
2. Если Issue нет — создать: заголовок как у истории, в теле ссылка на `docs/stories/…` и критерии из файла. Не плодить вторую задачу на ту же историю.
3. Дальше — цикл задачи ниже. Не спрашивать «с чего начнём?», если следующая история однозначно следует из роадмапа.
4. Одна сессия — как правило одна история / один PR. Не начинать следующую до merge текущей, если пользователь не сказал иначе.

## Роли

Основной агент (Claude Opus) координирует задачу и проектирует интерфейс; объёмную работу отдаёт субагентам из `.claude/agents/`:

| Субагент | Модель | Шаг |
|---|---|---|
| `acceptance-tests` | Claude Sonnet | 3 |
| `implementer` | Claude Sonnet | 4 |
| `reviewer` | Claude Opus | 6 |

## Цикл задачи

1. **Ветка.** От свежего `main`: `git switch -c issue-N-кратко`. Одна задача — одна ветка — один PR.
2. **Интерфейс.** Основной агент объявляет публичные типы и функции, нужные истории, с телами `todo!()`. Код должен компилироваться. Коммит.
3. **Приёмочные тесты.** Субагент `acceptance-tests` пишет интеграционные тесты по критериям приёмки истории. Тесты компилируются и падают. Коммит `test: приёмочные тесты для #N`. Пользователь просматривает тесты до начала реализации.
4. **Реализация по TDD.** Субагент `implementer`: модульный тест → минимальный код → рефакторинг → `scripts/check.sh`, пока приёмочные тесты не пройдут.
5. **Проверка.** Основной агент сам запускает `scripts/check.sh`; он должен пройти целиком.
6. **Ревью.** Субагент `reviewer`, исправить найденное, снова `scripts/check.sh`. Затем `git push` и `gh pr create` со ссылкой `Closes #N`.
7. **Слияние.** Только когда пользователь явно написал «Сливай» и CI зелёный: `gh pr merge N --merge --delete-branch`, затем `git switch main && git pull`.

## Жёсткие правила

- Приёмочные тесты (`tests/` крейта) не менять и не удалять без явного согласия пользователя. Если тест кажется неверным — остановиться и спросить.
- Комментарий писать только там, где код сам правило не показывает. Не пояснять тип, поле, функцию или вариант ошибки пересказом имени.
- Не ослаблять линты: никаких `#[allow(...)]` для `cognitive_complexity` и `too_many_lines`. Длинную или сложную функцию разбивать.
- Не писать код, который не требуется падающим тестом.
- Задача не готова, пока `scripts/check.sh` не проходит.
- PR не сливать без явного «Сливай» от пользователя. Одобрение кода или «замечаний нет» — не команда слить.

## Архитектура ради тестов

- Вся логика предметной области (счета, категории, операции, номера внутри дня, долги, отчёты) — в отдельном крейте без зависимостей от браузера и WASM. Он тестируется обычным `cargo test`.
- Google Drive и время (`сегодня`) — за трейтами; в тестах подставляются реализации в памяти.
- Слой интерфейса тонкий: только отображение и вызовы предметного крейта.
- Крейты: `crates/domain` — логика, `crates/web` — интерфейс на Leptos 0.8 в режиме CSR (API версии 0.8, не 0.6 и не 0.9). Запуск: `trunk serve` в `crates/web`.

## Тесты

- Приёмочные: `<крейт>/tests/story_NNN_<тема>.rs`, по тесту на каждый критерий. Над тестом — комментарий с номером истории и заголовком критерия, например `// 007 «Обязательные поля»`.
- Модульные: в модуле `#[cfg(test)] mod tests` рядом с кодом.
- Критерии про внешний вид («малозаметное поле») автотестами не покрываются; перечислить их в описании PR для ручной проверки.

## Однотипный код

Одинаковые конструкции писать одинаково. Если список в одном месте разбит по элементу на строку, соседний такой же список тоже разбивать по элементу на строку, а не собирать в одну. Подкатегории, поля и аргументы писать по одному элементу на строку, чтобы не проматывать экран вправо. `rustfmt` схлопывает короткий массив в одну строку — на таком объявлении ставить `#[rustfmt::skip]`.

## Экономия контекста

- Запускать `scripts/check.sh`, а не отдельные команды с подробным выводом.
- Читать только файлы, нужные для текущей истории.
