# Журнал эксперимента

## 2026-11-21 — Подготовка окружения и тулинга

**Цель сессии:** понять порядок работы и настроить инструменты, чтобы агент мог работать с GitHub.

**Решения:**
- Задачи и баги ведём в GitHub Issues, агент читает их через `gh`.
- Пользовательские истории храним в репозитории (`docs/SPEC.md`, `docs/stories/*.md`), а не в issues: они версионируются вместе с кодом и не «закрываются».
- Ревью PR — Bugbot (локально через `/review-bugbot` или облачный через GitHub-интеграцию).
- Порядок работы: спецификация → выбор стека → `AGENTS.md` → скелет + CI → нарезка задач → цикл «issue → PR → ревью → merge».

**Сделано:**
- Добавлен `shell.nix` (rustup, wasm-pack, sfz, gh), запушен в `main`.
- `gh` залогинен, протокол SSH, права `repo`, `workflow`.
- `git` и `gh` добавлены в allowlist команд Cursor.
- Проверено: агент видит `git`, `gh`, `cargo 1.99.1`, цель `wasm32-unknown-unknown`; доступ к `origin` по SSH работает.

**Что не получилось с первого раза:**
1. Агент не смог запустить shell (`Failed to exec /run/current-system/sw/bin/bash`), а потом не нашёл `git`. Причина: команды агента идут в песочнице, где не виден `/run/current-system` (системные пакеты NixOS). У пользователя в терминале всё работало.
2. `gh auth status` у агента показывал «token invalid», хотя пользователь был залогинен. Причина: токен в keyring, доступ к нему идёт через D-Bus, а сокет D-Bus в песочнице недоступен.
   - Решение для обоих пунктов: добавить `git` и `gh` в allowlist (Cursor Settings → Agents → Approvals & Execution). Такие команды выполняются вне песочницы.
3. Если агент сам запрашивает для команды сетевое разрешение, она уходит в песочницу даже при наличии в allowlist и падает без `git`.
4. Перелогин `gh` на SSH оказался не обязателен (`origin` и так был по SSH), но при этом пропало право `workflow`. Вернули через `gh auth refresh -s workflow`.
5. Агент в режиме Ask не может создавать файлы — этот журнал пришлось записывать отдельно.

**Ручное вмешательство:** вся настройка окружения (`shell.nix`, логин `gh`, allowlist, коммит) — руками; агент диагностировал и советовал.

**Следующий шаг:** спецификация в новом чате в режиме Agent.

## 2026-11-21 — Спецификация продукта

**Цель сессии:** сформулировать продуктовую спецификацию и пользовательские истории первой версии. Стек не выбираем, код не пишем.

**Формат работы:** агент задавал по одному-два вопроса за раз, ничего не придумывая за пользователя (22 вопроса), затем предложил план документов и после согласия с поправками записал файлы.

**Решения:**
- Покупкомер — веб-приложение для учёта личных финансов, для одного человека; сначала для автора, но сразу пригодное для других. Общего доступа нет.
- Мотивация: в EasyFinance и ZenMoney непонятно планирование и нельзя смотреть траты по подкатегориям. Долгосрочная цель — план из истории (среднее за 3 полных прошлых месяца по категории) и сравнение с ним текущего месяца.
- Первая версия — фундамент для данных: вход, настройка категорий, счета, ввод операций, быстрый доступ к остаткам и долгам, отчёт по категориям. Планирование — через несколько месяцев, когда будут данные.
- Вход через Google-аккаунт, данные в Google Drive (Application Data folder). Собственного сервера нет — жёсткое требование, в том числе для авторизации.
- Счета с валютой и начальным остатком; несколько валют без базовой валюты и пересчёта.
- Одно дерево категорий из двух уровней; у категории признак «для расходов / доходов / обоих»; подкатегория наследует настройки родителя. Удаление категории — с переносом операций в выбранную категорию.
- Операции: расход, доход, перевод (две суммы при разных валютах), дать в долг, взять в долг, частичный возврат долга. Автоматический порядковый номер внутри дня.
- Главный экран — лента последних операций и быстрое добавление.
- Не в первой версии: планирование, импорт, базовая валюта и курсы, офлайн/PWA, закрытие счетов, фильтры, метки/магазины/разбивка чека.

**Сделано:**
- `docs/SPEC.md` — что это, для кого, понятия, сценарии, что не входит, открытые вопросы.
- `docs/stories/001…014` — по файлу на историю, критерии приёмки в формате Дано/Когда/Тогда.

**Что не получилось с первого раза:**
1. Агент сразу ушёл в планирование (как считать среднее, как сравнивать середину месяца), хотя это задача второй-третьей очереди. Пользователь вернул к основе: сначала ввод операций, категории и счета.
2. В плане документов агент назвал «список операций», не пояснив, что имеет в виду; пришлось уточнять. Выяснилось, что это главный экран приложения.

4. В историю входа агент сначала заложил вариант с минимальным сервером для refresh token; после решения «без сервера» критерии ослаблены: пароль не вводится, но допускается одно нажатие для подтверждения через Google.

- Правила ревью — в `docs/REVIEW.md`. Bugbot есть только в Cursor, поэтому от него отказались: ревью делает субагент `reviewer`, `.cursor/BUGBOT.md` удалён.

## 2026-11-21 — Закрытие открытых вопросов спецификации

**Цель сессии:** ответить на открытые вопросы из `docs/SPEC.md` и историй до начала разработки, чтобы агенты не придумывали модель данных сами.

**Формат работы:** агент собрал вопросы из всех файлов и разделил на две группы: «влияют на модель данных — решить сейчас» и «можно решить перед своей историей». Пользователь ответил на все сразу. Агент записал ответы в спецификацию и истории и отдельно перечислил, что додумал сам, — пользователь подтвердил. Ответы породили новые вопросы; на них ушёл второй заход.

**Решения:**
- Несколько устройств, но не одновременно: приложение проверяет поле `version` файлов в Drive при возврате во вкладку и перед каждой записью и при изменениях перечитывает данные. Push-уведомления Drive требуют своего сервера и не подходят.
- Данные — JSON в нескольких файлах, а не реляционная база. Записи самодостаточны: имя контрагента копируется в операцию.
- Операцию можно отнести и к категории верхнего уровня, и к подкатегории. В отчёте сумма родителя включает всё; отдельной строки «без подкатегории» нет.
- Категорию с подкатегориями нельзя удалить или вложить в другую. Признак применимости — только фильтр при вводе, внесённые операции не трогает.
- Валюту счёта с операциями менять нельзя.
- Долги: один тип возврата с направлением; встречные долги не сворачиваются; возврат больше остатка или без долга запрещён; правка долга, после которой возвраты не сходятся, запрещена.
- Контрагент — список для быстрого выбора; новое имя попадает в список; переименовать или удалить можно только без долгов.
- Тип операции можно менять при редактировании.
- Отчёт: дерево за месяц или неделю (по умолчанию текущий месяц); помесячные суммы по категории — за всё время, с прокруткой влево от текущего месяца.

**Сделано:**
- Обновлены `docs/SPEC.md` и истории 001–005, 007, 008, 010–012, 014; открытым остался только отложенный вопрос о закрытии счетов.
- Стартовый набор категорий (002) сгенерировал агент, пользователь отредактировал.

## 2026-11-22 — Ввод расхода ([#6](https://github.com/markshevchenko/buy-o-meter/issues/6))

**Цель сессии:** первая операция в `crates/domain` — расход с датой, счётом, категорией, суммой и комментарием.

**Решения:**
- Дата — `SystemTime` в полночь UTC. Своего календарного типа нет: в стандартной библиотеке нет даты, а сутки прибавляются через `Duration`. Часы по-прежнему за трейтом `Clock`, в тестах — `FixedClock`.
- Порядковый номер внутри дня отдельно не хранится. Порядок — место в `expenses()`: по дате, внутри дня в порядке добавления. Расход за вчера встаёт в конец своего дня.
- Форма — `NewExpense`. `open` подставляет сегодня и пустые счёт, категорию, сумму и комментарий. Пустые обязательные поля — `DomainError::MissingFields`, расход не сохраняется. Несуществующий счёт или категория тоже не принимаются.
- Сумма уменьшает остаток своего счёта через `OperationDraft::Expense` и входит в `expense_total` этой категории и её родителя. Валюта — валюта счёта. Если в итоге встречаются две валюты, сумма не возвращается: `MixedCurrencies`. В `Record` расход не копируется; старые итоги по `add_record` не менялись.
- Комментарий писать только там, где правило не видно из кода. Это было в журнале сессии про счета, но не в `AGENTS.md`, поэтому агент правило не видел. Теперь оно в `AGENTS.md` и `docs/REVIEW.md`.

**Сделано:**
- Ветка `issue-6-expense`, PR [#21](https://github.com/markshevchenko/buy-o-meter/pull/21). Девять приёмочных тестов 007, `scripts/check.sh` зелёный.
- Малозаметное поле комментария автотестом не покрыто: экрана в этой истории нет.

**Что не получилось с первого раза:**
1. Комментарии пересказывали имена типов. Пользователь напомнил, что просил так не писать.
2. Свой `Date` без проверки корректности. Пользователь заменил его на `SystemTime` в полночь.
3. Отдельное поле порядкового номера. Пользователь убрал его: номер — это место в массиве.
4. Ревью: итог категории складывал рубли и доллары, а расход можно было записать на несуществующий счёт или категорию. Оба случая закрыты модульными тестами.

**Ручное вмешательство:** просмотр приёмочных тестов, запрет комментариев-пересказов, отказ от своего `Date` и от хранимого номера.

**Следующий шаг:** история 008 «Ввод дохода» ([#7](https://github.com/markshevchenko/buy-o-meter/issues/7)).

## 2026-11-22 — Перевод между счетами ([#8](https://github.com/markshevchenko/buy-o-meter/issues/8))

**Цель сессии:** перевод между своими счетами, в том числе в разных валютах. Остатки меняются на свои суммы.

**Решения:**
- Форма — `NewTransfer`: дата (по умолчанию сегодня), счёт списания, счёт зачисления, `amount`, `to_amount`, комментарий. Категории нет.
- Одна валюта: вводится `amount`, `to_amount` пустой; в записи зачисленная сумма равна списанной. Разные валюты: списывается `amount`, зачисляется `to_amount`. Сколько полей суммы показывать — `Ledger::transfer_amount_fields`: `One` или `Two`.
- Один и тот же счёт — `DomainError::SameAccount`, список переводов и остатки не меняются.
- Общие помощники приёмочных тестов — `crates/domain/tests/common/mod.rs`: `create_account`, `create_top`, `create_child`. Файл `common.rs` прямо в `tests/` Cargo собрал бы отдельным крейтом, соседние истории его бы не видели. `#![allow(dead_code)]` стоит на этом модуле: каждая история — свой крейт и вызывает не все функции.
- Пустые счета или сумма — `DomainError::MissingTransferFields`. Разные валюты без `to_amount` — та же ошибка с флагом `to_amount`, перевод не сохраняется. Нет ни одного счёта — `AccountRequired`. Идентификатор, которого нет в журнале, — `AccountNotFound`.

**Сделано:**
- Ветка `issue-8-transfer`, PR [#23](https://github.com/markshevchenko/buy-o-meter/pull/23). Пять приёмочных тестов 009 проходят, `scripts/check.sh` зелёный.
- Перевод пишется в `transfers()` по дате, внутри дня в порядке добавления. Остатки меняются через `OperationDraft::Transfer`.
- Те же помощники подключены в историях 003, 005, 007 и 008. Проверки критериев не менялись.
- Малозаметное поле комментария автотестом не покрыто: экрана в этой истории нет.

**Что не получилось с первого раза:**
1. Пустой `to_amount` при разных валютах подменялся суммой списания: 7 500 рублей зачислялись как 7 500 долларов.
2. Пустые поля отвечали `AccountNotFound`. Без единого счёта перевод не отвечал `AccountRequired`, в отличие от расхода и дохода.

**Ручное вмешательство:** просмотр приёмочных тестов, вынос повторяющихся `create_account`, `create_top` и `create_child` в общий модуль. Пользователь убрал критерий и тест «Не влияет на отчёты по категориям»: у перевода нет категории, отдельного правила тут нет. Тест пишется только на то, что реализация может нарушить. Это записано в `AGENTS.md`.

**Следующий шаг:** слияние после «Сливай» и зелёного CI.
